## 1. What Step 15 delivers

Step 14 shipped circulars that only a moderator could create by hand; Step 15 adds the admin workflow that makes them trustworthy:

1. **Verification queue** — `/admin/jobs/circulars` (tabs: pending / returned / draft / verified / published / rejected / all, counts from one capped query, `?tab=` in the URL) + a rewritten `/admin/jobs` hub with real tiles (pending verification, returned, published, reports, open corrections).
2. **Circular editor + verification workspace** — `/admin/jobs/circulars/new` and `/admin/jobs/circulars/:id`: full circular form (all 10 design fields, Asia/Dhaka date+time inputs that never shift the day through the browser timezone, date-only deadlines never invent 11:59 PM), duplicate warnings, source/apply links with a live domain check, and the **7-point evidence-based checklist** (pass/fail/uncertain/na + per-item notes, checked by the verifier — never a bare checkbox). Actions: save / submit for verification / approve / request changes / reject / publish / withdraw / delete (Admin-only, audit-first) / update published facts (reason + official source link required).
3. **No self-approval** — `canApproveCircular`: author ≠ verifier, last editor ≠ verifier; the owner may override only with a reason ≥10 chars, recorded in the audit log. The guard is enforced in the UI and the approve function; the rules allow the key but do not re-check the ticks (compiled-rules margin — a rules-side checklist check is a post-refactor follow-up).
4. **Audit trail** — `circularHistory`: one append-only doc per sensitive change (deadline, source/apply link, post count, review status, exam date, start date; plus explicit duplicate/correction/extension/relationship records). History is best-effort in the client: if its rules are not live yet, the admin action still completes, the adminActions entry is the audit that landed, and the caller is told history is pending — never silently dropped. `adminActions` gained the `'job-content-deleted'` action (delete writes the audit entry FIRST).
5. **Report incorrect info** — "তথ্যে ভুল আছে? রিপোর্ট করুন" on every published circular detail page + a correction-proposal form. Reports (`jobReports`) and corrections (`jobCorrections`) are stored for admin review and **never auto-change verified info**: deciding a report/correction only records the outcome; the circular changes only through the editor workflow with the official source verified. Admin inboxes: `/admin/jobs/reports`, `/admin/jobs/corrections`.
6. **Approved official domains** — `/admin/jobs/domains`: admin-managed `approvedDomains` list (one doc per domain; multiple domains per org; statuses active/watch/deprecated; suspend = soft action, history preserved). Until its rules deploy, the editor checks against the 9-entry code list in `src/lib/jobOfficialDomains.ts` (BPSC, BPSC Teletalk, BB e-recruitment, bb.org.bd, DPE, DPE Teletalk, NTRCA, NTRCA Teletalk, teletalk.com.bd as watch) and says so honestly. The check is exact-hostname-or-subdomain-boundary + HTTPS required — never substring matching.
7. **Duplicate detection** — dedupe key `examSlug__<normalised memo>__<published year>` (null without a memo number — no key invented) + a similarity check (same exam + title-token Jaccard ≥0.5 + deadline within ±7 days). Surfaced as a warning card in the editor; never auto-delete/merge.
8. **Verification labels** — Verified / Unverified / Updated (সংশোধিত — an official correction/extension, shown via "সর্বশেষ হালনাগাদ" + history) / Archived (closed circulars stay readable). Labels describe SOURCE VERIFICATION, never application status. Source preference: recruiting org's website → official govt recruitment/application portal → govt-hosted circular PDF → official govt notice/correction. No circular becomes verified just because an admin added it, a Facebook page shared it, a coaching center published it, another job site lists it, or the link works.

## 6. Explicit reconciliations

- **R1 — Lifecycle vs live collection.** Gemini's single lifecycle, ChatGPT's three-field split, and Step 14's live `circulars` + `reviewStatus` reconcile onto the existing collection: draft → in-review → verified → published; changes-requested = in-review → draft + reviewNote; rejected = in-review → rejected. The live collection is NOT renamed. The three-field split's distinctions survive as workflow states, not stored fields.
- **R2 — Revisions vs amendments vs history.** ChatGPT's immutable revisions subcollection vs Gemini's amendments array + original/current fields reconcile into ONE approach: top-level append-only `circularHistory` + existing `adminActions`. Reasons: a revisions subcollection needs rules room that does not exist (see §3) and doubles write cost; an amendments array needs allowlist keys + margin. The original values are preserved as history entries' previousValues.
- **R3 — Anonymous reports.** ChatGPT allows them; Gemini wants authenticated-or-rate-limited. Reconciled to authenticated-only in v1: an open create rule with no rate limiting and no Cloud Functions is a spam vector on Spark free. Anonymous reporting is a Phase 3 item if abuse controls exist.
- **R4 — Rules margin.** Both AIs' role-enforced rules + new collections breach the ~209-byte margin (measured: full candidate 260,991, over by 4,991). Measured first, before writing the UI: the rules parts that breach are written + emulator-verified but deploy-blocked; UI + client logic within existing rules ships first. The public-ID refactor (23 Nov 14:30 cron) frees ~4,992 bytes, which is what makes the deferred rules deployable later — staging does not depend on it.
- **R5 — Role store.** Gemini's `adminUsers/{uid}` is rejected in favour of the existing `users/{uid}.role` + `AdminGuard` (owner/admin/moderator/teacher). No parallel role store.
- **R6 — Audit location.** Gemini's `jobCirculars/{id}/auditLogs` subcollection is adapted to top-level `circularHistory` so the queue reads recent changes across ALL circulars in one query.
- **R7 — Checklist model.** Gemini's booleans are adapted to ChatGPT's evidence-based results (pass/fail/uncertain/na + notes), same 7 items, same blocking semantics, plus the na case.
- **R8 — Domain storage.** Gemini's single `config/officialDomains` doc is adapted to one doc per domain in `approvedDomains` (add/suspend without rewriting a shared doc).
- **R9 — Notifications.** Both AIs discuss a Notification Admin / notifications screen; it is NOT built in this step (Step 14's in-app centre is derived client-side with no collection). Deferred to Step 16+ notification work.
- **R10 — Updated label.** ChatGPT's post-publication Updated/Archived/Withdrawn states: Updated is shown via "সর্বশেষ হালনাগাদ" + history in v1 (a dedicated student-facing "what changed" list is a follow-up); Archived = closed circulars stay readable; Withdrawn = unpublished via rejected with a reason.
