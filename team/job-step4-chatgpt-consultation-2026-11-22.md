## Full answer (verbatim)

Eduvelto Step 4 — Technical Design Review

Overall verdict: Approve with changes required before closure.

The design is fundamentally sound. In particular, keeping Job Preparation preferences on the existing user document, validating them in Firestore rules, avoiding mandatory registration fields, and refusing to automatically upload anonymous drafts are good decisions for a Firebase Spark project without Cloud Functions.

However, I would not close Step 4 yet.

There are several issues worth addressing before Step 5 builds on this data model:

1. Firestore validation needs stronger guarantees around uniqueness, integer values, document creation, and field ownership.
2. The local-draft implementation needs protection against cross-account contamination and stale values.
3. The profile model needs to distinguish missing configuration from intentionally cleared configuration.
4. Step 5 needs a stable category/exam relationship rather than relying on independent lists of slugs.
5. The onboarding flow needs a better way to encourage completion without forcing students.

### (a) Security gaps

The existing rules design has the right general security approach: client-side validation is useful for UX, but Firestore rules independently enforce the actual constraints. The 202 passing tests are encouraging. However, passing tests demonstrate the tested cases, not necessarily every possible malicious write.

**1. Role escalation.** The role-escalation test is important: valid Job fields plus a role change must fail; isActive changes must fail; verificationStatus changes must fail. This is correct. However, one additional area to explicitly verify: the user-document creation rule. A malicious authenticated user might attempt to create their own document with role "admin", verificationStatus "verified", isActive true, enrolledCategories ["bank"], jobOnboarded true. Excluding role from the update allowlist does not automatically protect document creation. The create rule must explicitly enforce that: a student cannot create an admin or teacher account; verification status cannot be self-assigned; administrative privileges cannot be assigned through initial document creation; any privileged fields are either prohibited or assigned only safe initial values. This is especially important because Eduvelto does not have Custom Claims or a trusted Cloud Functions writer. Recommendation: treat the create rule and update rule as separate security boundaries. Test both independently. Also, be careful with the existing admin/owner authorization model. If administrative authorization relies on a role stored in Firestore, there must be a trustworthy process for assigning that role. A role field that users can assign themselves during account creation is not a security boundary.

**2. Category validation: add uniqueness.** Current validation: must be a list; maximum 10 elements; toSet().hasOnly(the 10 category slugs). A list containing duplicate values can still pass the allowed-values check — e.g. ["bank", "bank", "bank", "bank"]. Recommend adding: enrolledCategories.toSet().size() == enrolledCategories.size(). Keep the maximum size check as well.

**3. Daily goals must be integers.** Current constraints: dailyGoalQuestions 0–500; dailyGoalMinutes 0–600. Explicitly require integers, otherwise 12.5 / 45.75 may pass range validation. Use integer validation in Firestore rules, not just HTML input attributes. Also verify: negative values fail; values above the maximum fail; floating-point values fail; strings containing numbers fail; booleans fail. The last three are particularly important because JavaScript and Firestore have different type-coercion behavior.

**4. Missing fields versus null.** The design permits null for target exam and daily goals. That is reasonable, but make sure the rules deliberately distinguish: a field that is missing; a field explicitly set to null; a field with an invalid value. For example, dailyGoalQuestions should not silently accept an arbitrary string or an unexpected object simply because the field is optional. For every Job field, define whether it is: required on document creation; optional on document creation; allowed to be removed; allowed to be explicitly null. Also verify that an update cannot bypass validation by deleting a field that is supposed to remain mandatory.

**5. Prevent unexpected fields.** The update rules should validate the complete set of modified fields using an allowlist — conceptually changedKeys.hasOnly(allowedEditableFields). For creation, use a separate permitted-key check. Do not rely solely on validating the five new fields. A user must not be able to introduce unrelated privileged fields through an otherwise valid Job update.

**6. Local drafts are not a security boundary.** The localStorage mechanism does not itself create a Firestore security vulnerability if all profile writes are independently validated by Firestore. A student can modify localStorage through browser developer tools. That is expected. The important distinction is: localStorage values are untrusted input; React validation is UX; Firestore rules are the security boundary. The decision to revalidate local values before using them is correct. Security verdict: keep the overall approach, but add uniqueness and integer validation, explicitly harden account creation, and test deletion and unexpected-field cases.

### (b) Profile model: enrolledCategories, targetExam and daily goals

Keep the model, with one important adjustment. Do not introduce a separate collection for these five fields in Step 4. For the current scale, keeping preferences on users/{uid} is appropriate.

**1. enrolledCategories.** Keep it as an array of category slugs. Advantages: easy to read when loading the student dashboard; easy to update through ProfilePage; no additional Firestore reads; easy to validate against a fixed allowlist; removing a category does not require deleting progress. Important: category enrollment must not be confused with category progress. Keep these concepts separate: enrolledCategories = student's selected interests/enrollments; question attempts = actual activity; completed topics = learning progress; exam results = performance history. Removing a category must never delete historical attempts, scores, or completion records. The existing explanatory note is good.

**2. targetExam.** This is the field to reconsider before Step 5. Currently targetExam: "bank-officer" works if the student has exactly one target exam across all enrolled categories. But a student enrolled in Bank AND Government may want both a Bank Officer target and a Government primary teacher target — one global targetExam cannot express both goals. Option A — keep one targetExam (recommended for Step 4): keep the current field if the product intentionally supports one primary target exam. Document that it means the student's primary examination target, not a complete list of all examination interests. Simple and appropriate for the current stage. Option B — introduce category-specific targets (e.g. examTargets: {bank: "bank-officer", government: "primary-teacher"}). Do not implement this prematurely — it introduces more complicated validation, migration, editing, and UI behavior. Recommendation is Option A for Step 4, with one explicit architectural constraint: Step 5 must not assume that one global targetExam represents every category-specific exam preference. If multiple targets become a confirmed requirement, migrate deliberately.

**3. Daily goals.** Keep both fields (dailyGoalQuestions: 30, dailyGoalMinutes: 60). The separation is useful. Null defaults are the correct choice. Do not introduce fake 30/30 defaults. However, document the meaning of zero: null = no goal configured; 0 = goal explicitly set to zero; positive integer = actual daily target. This distinction must be consistent across the profile form and dashboard. One additional future consideration: daily goals should not become progress data. A goal of 30 questions is a preference; actual completion must be calculated from recorded activity.

**4. jobOnboarded.** Keep this boolean. It has a clear purpose: whether the student has dismissed or completed the initial mode-choice experience. It should not be interpreted as whether the student completed their profile, enrolled in a category, selected an examination, or started learning. A student who chooses "decide later" is onboarded in the narrow sense that the introductory screen has been handled. That is acceptable.

**5. Recommended model for Step 4.** Retain the five fields (enrolledCategories: string[]; targetExam: string | null; dailyGoalQuestions: number | null; dailyGoalMinutes: number | null; jobOnboarded: boolean). Keep jobMode as its existing separate preference. The important thing is to avoid mixing preferences with actual educational activity.

### (c) Onboarding UX: once-only, non-modal card

Good decision. Agree with using a non-modal card instead of a blocking modal. For a free education platform serving students with different levels of digital familiarity, a blocking first-time screen can create unnecessary friction. Strengths: students can explore the dashboard without making an immediate decision; beginners are not forced to identify themselves as advanced; students can dismiss the choice; the same copy is used in the onboarding screen and mode switch; signed-out visitors are not forced into account creation; students can reopen the choice later. These are good UX decisions.

The main problem: students may never configure anything. A student can sign in, see the mode-choice card, select "decide later", dismiss the card, never visit ProfilePage, never select a category or exam. This is not a technical failure, but it can result in a poorly configured dashboard. Do not solve this by making all fields mandatory. Instead, introduce progressive completion. On first visit: show the existing mode-choice card. After choosing a mode or deciding later: dismiss the card permanently. On the Job dashboard: if no categories are selected, show a small contextual prompt ("আপনার পছন্দের প্রস্তুতির বিভাগ নির্বাচন করুন।") with a clear link to profile settings. If no target exam is selected, show a separate optional prompt. If no daily goals are configured, show a third optional prompt only where useful. These should not become three persistent warning banners. A compact profile-completion section would be sufficient.

Beginner/Advanced default: the decision that an absent mode means Beginner is sensible, provided the application uses this default consistently. Make one distinction: missing jobMode means Beginner by application default; explicitly selecting Beginner should save Beginner; selecting Advanced should save Advanced. This makes the default deterministic.

Reopening the mode choice: the "show mode choice again" button is useful. But reopening the choice should not accidentally reset enrolled categories, target exam, daily goals, or learning progress. Only the mode preference should change when the student changes modes.

UX verdict: keep the non-modal, once-only card. Add lightweight dashboard prompts for incomplete configuration rather than making onboarding mandatory.

### (d) Signed-out local drafts and profile conflicts

Changes required. This is the area to pay the most attention to after Firestore security. The core policy is correct: the authenticated Firestore profile wins; anonymous local drafts must never be automatically uploaded. That is the safest default. However, the current implementation has a potential cross-account data contamination problem.

**1. Cross-account localStorage contamination.** Currently using global keys: eduvelto-job-categories, eduvelto-job-target-exam, eduvelto-job-daily-goal. ProfilePage also writes profile values back into localStorage when signed in. Consider: Student A signs in, saves Job preferences, ProfilePage writes them into global localStorage keys, Student A signs out, Student B signs in on the same browser, opens ProfilePage, Student B's Firestore profile has no Job preferences, the application finds Student A's values in localStorage, Student B now sees Student A's preferences as draft values. Even if nothing is automatically uploaded, this is undesirable. It can also occur on shared family devices and school computers. Required change: separate anonymous and authenticated storage. Anonymous drafts: eduvelto-job-anonymous-categories, eduvelto-job-anonymous-target-exam, eduvelto-job-anonymous-daily-goal. Authenticated fallback/cache: eduvelto-job-profile-{uid}-categories, eduvelto-job-profile-{uid}-target-exam, eduvelto-job-profile-{uid}-daily-goal. The UID-specific cache must never be treated as another student's draft. Alternatively, eliminate authenticated localStorage fallback entirely and use Firestore as the only authenticated source of truth. That would be even simpler. For a zero-budget application, the simpler arrangement is favoured: anonymous visitors use localStorage drafts; authenticated students use the Firestore profile; optional authenticated cache is UID-namespaced only.

**2. Stale anonymous drafts.** A student visits while signed out, selects Bank and Government, leaves, returns weeks later, registers or signs in, and their profile already has a different selection. The profile-wins policy handles this correctly if the Firestore profile is complete. But the current prefill behavior introduces ambiguity when a profile field has no value — e.g. Firestore targetExam: null vs localStorage targetExam: "bank-officer". Does null mean the student has never selected an exam, intentionally removed their exam selection, or the profile was initialized without this preference? Those are different situations. The same problem exists with empty arrays and daily-goal null values. Required change: define explicit precedence — signed out: read and save anonymous local drafts; signed in with a configured Firestore value: Firestore wins; signed in with an explicitly empty Firestore value: Firestore wins; signed in with no historical Firestore value: offer anonymous draft import if one exists; student rejects import: keep Firestore unchanged; student accepts import: validate and save through normal profile flow. Important detail: [] and null should count as actual stored values, not automatically as missing values. If distinguishing never-initialized fields from intentionally cleared fields is needed, use document field presence or an explicit schema/version marker. Do not infer this distinction from truthiness.

**3. Should there be a merge prompt?** Yes, but only as an explicit import decision. Do not implement an automatic merge. Example: anonymous draft has enrolledCategories ["bank", "government"], targetExam "bank-officer"; authenticated profile has enrolledCategories ["primary-teacher"], targetExam null. Automatically merging the arrays would change the student's existing profile without permission. Automatically choosing the draft's exam would also override their existing preference. Instead, display a small prompt: "আপনার আগে সংরক্ষিত কিছু প্রস্তুতির পছন্দ পাওয়া গেছে। আপনি কি সেগুলো প্রোফাইলে যুক্ত করতে চান?" Provide: Import draft / Keep profile unchanged / Review draft. The import action must use the normal profile save flow and Firestore rules.

**4. Clear anonymous drafts after account resolution.** After a successful import, clear the anonymous draft. If the student declines, clear it after confirmation or retain it only as an explicitly separate anonymous draft. Do not leave an old draft available indefinitely without clear ownership.

**5. What about two devices?** The profile-wins policy handles this well: Device A saves Bank, Device B saves Government, Firestore is the authoritative state, the next profile load reads the latest server state. Do not attempt to synchronize two independent local drafts automatically. Also, make sure the profile update does not overwrite unrelated user-document fields.

Verdict: keep "profile wins, never auto-upload", but introduce an explicit anonymous-draft import decision and prevent global localStorage values from crossing account boundaries.

### (e) Other changes required before Step 4 closes — especially Step 5 compatibility

**1. Prepare for the Step 5 category and exam structure.** Most important architectural consideration. Currently: 10 category slugs, 14 accepted examination slugs, 13 examinations visible in the UI, one future examination (it-professional). Acceptable as an intermediate implementation, but the application must avoid maintaining several inconsistent definitions of the same taxonomy. Recommend a central TypeScript configuration (JOB_CATEGORIES as const; JOB_EXAMS category-specific exam definitions) used for: category checkboxes, examination dropdowns, dashboard category labels, category filtering, exam selection, validation in the application, future Step 5 hub navigation. Firestore rules cannot import TypeScript configuration, so their allowlists will remain separately maintained — that creates a synchronization responsibility. Add a test that compares the frontend taxonomy against an independently maintained expected taxonomy, so accidental omissions are caught. Specific recommendation for it-professional: keep the slug accepted by Firestore rules, but do not expose it as a selectable examination until its hub and associated content are implemented. When Step 5 introduces it, update the UI and taxonomy tests together.

**2. Define the category-to-exam relationship.** Currently the model validates enrolledCategories and targetExam independently, but does it validate that the target examination actually belongs to one of the student's enrolled categories? E.g. enrolledCategories ["bank"] with targetExam "primary-teacher" — both individually valid, but the combination is inconsistent. Recommend enforcing this relationship in the application. At minimum: the target exam must belong to a recognized category; selecting a target exam should either automatically select its category or require that category to be selected; removing the category associated with the current target exam should trigger a clear decision (e.g. "আপনি যে বিভাগটি সরিয়েছেন, সেটির সঙ্গে আপনার নির্বাচিত পরীক্ষাটিও যুক্ত। পরীক্ষাটি কি সরিয়ে দিতে চান?"). Do not silently leave an invalid combination. Whether to enforce this relationship in Firestore rules depends on the final taxonomy structure. With a small, fixed mapping, it is possible to enforce it there too. However, application-level enforcement alone is not sufficient if inconsistent combinations would cause security-sensitive behavior.

**3. Make profile saves safe against concurrent changes.** The existing ProfilePage form flow is reused. Verify that the implementation updates only the intended fields. Prefer targeted updates rather than replacing the complete user document with a potentially stale React state snapshot (e.g. updateDoc(userRef, {enrolledCategories, targetExam, dailyGoalQuestions, dailyGoalMinutes})). This avoids accidentally overwriting role, verification status, account status, other profile fields, or fields updated elsewhere. Also verify the behavior when two devices edit the same preferences. For this stage, last-write-wins is acceptable. No sophisticated conflict-resolution system needed. However, show a save error if Firestore rejects an update. Never display a success state merely because local React state changed.

**4. Audit the meaning of mode and onboarding together.** One detail deserves an explicit test. The following should all behave correctly: jobMode missing + jobOnboarded missing → show onboarding, default Beginner; jobMode missing + jobOnboarded true → no onboarding, default Beginner; Beginner + true → no onboarding, Beginner selected; Advanced + true → no onboarding, Advanced selected; Advanced + false → show onboarding with existing Advanced preference. The final row is particularly important: if a returning student has already selected Advanced but somehow has jobOnboarded false, the onboarding screen should not silently replace their existing mode. Also, "decide later" should not write a fabricated Beginner preference unless explicitly intended. The current approach of setting only jobOnboarded: true is better.

**5. Account for zero verified teachers.** Not directly a Step 4 defect, but it affects how the profile and dashboard should be presented. There are currently zero verified teachers. Therefore: a selected category must not imply that verified question content exists; selecting an exam must not imply that exam preparation is currently available; an empty category must not look like a broken dashboard; the interface must distinguish preferences from available learning content. For example: a student can select Bank preparation today, even if verified Bank questions are not yet available. The dashboard should communicate that honestly. Never publish unverified questions merely to make the selected category appear populated.

**6. Add regression tests for the full flow.** The 20 new security tests are good, but Step 4 should not close based on security tests alone. Recommended integration scenarios: new student registration (no mandatory Job fields); first signed-in visit (onboarding displayed); choose Beginner/Advanced (mode and onboarding state saved); decide later (onboarding state saved, mode remains absent if previously absent); reopen mode choice (existing preferences unchanged); save categories (valid categories persist); duplicate categories (rejected); remove category (historical progress preserved); clear target exam (null persists correctly); set daily goal to zero (zero persists, not converted to null); set decimal goal (rejected); signed-out draft (stored locally only); sign in with existing profile (profile wins); sign in with anonymous draft (no automatic upload); two different accounts on one browser (no cross-account draft contamination); save failure (user receives an error); Step 5 adds it-professional (valid selection becomes available); refresh dashboard (saved preferences remain consistent). Also test a student changing categories while another browser session has an older profile snapshot.

### Prioritised must-change list before closing Step 4 (0/8 complete)

- P0 — Strengthen Job field validation — enforce unique category slugs, integer-only daily goals, valid types, and deliberate missing/null handling.
- P0 — Fix localStorage account isolation — separate anonymous drafts from authenticated UID-specific storage; prevent one student's preferences from appearing in another student's profile.
